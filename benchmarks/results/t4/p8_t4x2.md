# P8 on real GPUs — size-blind routing, Kaggle 2×T4

**Kaggle 2×T4, real engines; routing not exercised.** Two vLLM servers of one model on one Kaggle "GPU T4 x2" VM,
one per GPU. No EPP and no gateway: each probe is sent straight to L (the replica full of long prompts) or S (the
replica full of short prompts), the "forced to L / forced to S" rows of the simulated P8
([GAPS.md P8](../../../deploy/gateway/GAPS.md#p8--is-the-epp-size-blind)). What a router would have picked is
**computed offline from real engine metrics**, never "EPP picked".

**Current results: [Run 2](#run-2--measured-current)** (run 20261022-221119). Run 1 below is kept for the record; its loaded TTFT was phase-locked.

**Prompt sizes are real tokens.** The simulated P8 used `"<uuid> w0 w1 … wN"`, and the simulator counted one token per
word. Qwen's tokenizer splits digits, so 3,000 such words would be ~14K tokens, over `--max-model-len 8192`. Here the
same text is cut to 3,000 / 200 / 100 tokens with the served model's tokenizer, so the sizes match P8's token counts. The
chat template and uuid add a few tokens; each row records the engine's `usage.prompt_tokens`.

## Prediction (written before the measured run)

Inputs, all from earlier recorded T4 runs, not from this one:
- Prefill speed. Qwen2.5-3B at c=1 had TTFT p50 **94.6 ms** for 256-token prompts, mean SM clock 873 MHz (sweep
  20261014-220946, `closed-mnsdefault-c1`). That puts a floor of ~2.7K prompt tok/s on prefill, overhead included.
  At that floor a 3,000-token prefill takes ≤ ~1.1 s.
- Decode: TPOT p50 27.3 ms at c=1 and 30.1 ms at c=2 (same rows).
- KV pool: 175,008 tokens at `--max-model-len 4096` (baseline 20261014-215653, log). The pool comes from memory, not
  from max-model-len, so expect about the same at 8192.
- Chunked prefill: `enable_chunked_prefill=True` in the 0.31.0 engine config line of that baseline's server log.
  `--max-num-seqs` and `--max-num-batched-tokens` print `(default: None)` in `--help=all`, so they are resolved at
  engine-config time. This run records the resolved values (row `engine-config`).

What I expect, and why:
1. **Idle.** L ≈ S. TTFT 60–110 ms for a ~130-token probe, with the two GPUs within ~15 % of each other unless one
   session GPU is power-capped (that would show in the SM clock column).
2. **Main (L = 2 × 3K, S = 3 × 200, 64 out). The 7.2 s simulated gap does not reproduce; the real gap is sub-second.**
   The simulator had `max-num-seqs 2`, so its probe waited for a whole long request, decode included (7.75 s). vLLM's
   default admits the probe at once, and with chunked prefill it waits only for the prefill chunks scheduled ahead of
   it. The V1 scheduler serves running requests (including a partially prefilled long prompt) before waiting ones. Each
   long request cycles as ≤ ~1.1 s of prefill plus 64 × ~30 ms of decode, so L is prefilling a large share of the time.
   - Median TTFT(L): 0.3–0.6 s.
   - Max TTFT(L): ~1–2 s (probe behind both long prefills).
   - Median TTFT(S): 0.08–0.2 s.
   - Gap (median L − S): **0.2–0.5 s**; ratio **3–6×**.
   - ITL: the probe's p95 ITL on L well above S's, because steps that carry a prefill chunk are long; p50 ITL about
     the same on both (~30–40 ms).
3. **Long-output (512 out).** L spends most of its time decoding (512 × ~30 ms ≈ 15 s per request against ≤ ~1.1 s of
   prefill), so a probe seldom lands behind a prefill.
   - Median gap: under 0.1 s, likely not distinguishable from 0 at n = 12.
   - Max TTFT(L): still up to ~1 s.
   - Background output tok/s on L about 2× main's (more decode per prefill).
4. **Sweep (L only).** TTFT(L) grows with long-prompt size, roughly with one prefill's duration (1K < 3K < 6K), and
   with in-flight count (4 > 2: more of the time is spent prefilling).

**Router signals (prediction).** With the default `max-num-seqs`, neither server queues 2 or 3 requests: waiting = 0
on both, so the queue scorer ties (1/1). KV usage on L ≈ 2 × ~3.1K / 175K ≈ 0.035, on S ≈ 3 × ~0.3K / 175K ≈ 0.005. The
kv-cache scorer (`1 − usage`, weight 2) then gives S about +0.06, and unique prompts make prefix 0/0. **So the stock
sim-pool profile would score S higher on real engines.** That is the opposite of the simulated P8 (8 / 8 to the long
pod), where the simulator reported KV usage 0 and S had 1 waiting. The margin is small and comes from the kv scorer
alone. The token-load profile also prefers S, but only while a long prompt has not yet streamed its first chunk.

### Headline (main condition) — and why the TTFT gap understates the cost

| | L | S | L − S | 95 % bootstrap CI | ratio |
|---|---:|---:|---:|---|---:|
| probe TTFT median (s) | 0.186 | 0.138 | **0.047** | 0.022 … 0.061 | 1.34× |
| probe e2e median, 128 tokens (s) | 15.39 | 4.55 | **10.84** | 10.77 … 10.95 | 3.4× |

n = 5 per server (planned 12). Spread: TTFT L 0.161–0.193 s, S 0.124–0.141 s; e2e L 15.32–15.50 s, S 4.51–4.59 s.

**The TTFT numbers on L are a best case, not what a randomly arriving request pays.** L had at least one long request
dispatched but not yet streaming (prefill or queued) for **67.6 %** of the main window. Yet **0 of 5** L probes (and
0 of 10 probes overall, by the pre-send token load) were sent inside such a phase. Each probe left 1.4–2.3 s after a
long request's first chunk and 0.05–1.0 s before the next long request was sent (computed from `background.jsonl`).

The cause is the gate. "Hold the in-flight count for 5 s, before every probe" resets whenever a long request finishes
(the gauge dips while the closed loop re-sends). The two long workers ran in step, ~7.7 s per cycle (background e2e
p50 7.72 s), so the hold could only complete in the decode-only stretch after both prefills. The gate waited 7.7–49 s
per probe, with up to 11 resets. Arrivals were therefore phase-locked, and the 0.047 s gap is not the "forced to L"
number P8 asks for. That number was not measured in this run.

What the run does measure:
- **Decode on L stalls behind long-prompt prefill.** Every L probe shows 6 gaps above 0.5 s, the largest 2.19 s, 2.18 s,
  1.7 s, 1.7 s, ~1.4 s (steps that carry a 2,048-token prefill chunk). They add up to the 10.8 s e2e gap for a 128-token
  answer.
- **A long request on L itself waits 4.2 s (p50) for its first token**, against 0.29 s for a short request on S.

The GPUs were not at equal clocks. S (GPU 1) ran slower in both windows: idle 570 vs 652 MHz mean, main 957 vs
1,258 MHz. At idle, S's ITL was 44 vs 32 ms. That works against S, so the measured L − S gaps are not inflated by the
clock difference.

## What a router would have seen

**Computed offline from real engine metrics.** These are the pre-send /metrics snapshots of both servers for every
probe. llm-d-router v0.9.0 (tag `v0.9.0`, commit `5f4e762f`), the stock sim-pool profile
([deploy/gateway/p8/epp-p8.values.yaml](../../../deploy/gateway/p8/epp-p8.values.yaml) `baseline.yaml`: queue ×2, kv-cache ×2,
prefix ×3; picker defaulted to max-score):

| Piece | Formula | Source (`pkg/epp/…` at v0.9.0) |
|---|---|---|
| inputs | `vllm:num_requests_waiting` → WaitingQueueSize, `vllm:kv_cache_usage_perc` → KVCacheUsagePercent | `framework/plugins/datalayer/extractor/metrics/factories.go:92-94` |
| queue-scorer | `(max_w − w) / (max_w − min_w)`; all 1.0 when equal | `framework/plugins/scheduling/scorer/queuedepth/queue.go:95-99` |
| kv-cache-utilization-scorer | `1 − KVCacheUsagePercent` | `…/scorer/kvcacheutilization/kvcache_utilization.go:79` |
| prefix-cache-scorer | matched blocks / total blocks (unique prompts → 0) | `…/scorer/prefix/plugin.go:117-120` |
| weighted sum | `Σ clamp(score, 0, 1) × weight` | `scheduling/scheduler_profile.go:178`, clamp `:215-223` |
| max-score-picker | highest total; random shuffle breaks ties | `…/picker/maxscore/picker.go:92-102`; default picker `config/loader/defaults.go:189` |

| condition | n | L running / waiting / KV (mean of snapshots) | S running / waiting / KV | stock: higher score | median margin |
|---|---:|---|---|---|---:|
| idle | 24 | 0 / 0 / 0 | 0 / 0 / 0 | tie on 24 (random pick) | 0 |
| main | 10 | 2.00 / 0.00 / 0.0355 | 3.00 / 0.00 / 0.0051 | **S on 10 / 10** | **0.0611** |

Example (first main probe): L = queue 1.0 × 2 + kv 0.9645 × 2 + prefix 0 = 3.929; S = 2 + 0.9948 × 2 = 3.990.

**Verdict: on real engines the stock profile would score S (the short-prompt replica) higher.** This is the opposite of
the simulated P8 (8 / 8 to the long pod), where S had a queued request and the simulator reported KV usage 0. Here
vLLM's default `max-num-seqs` 256 means nothing queues, the queue scorer ties, and the kv scorer alone moves the
probe away from L. The margin is 0.061 out of a maximum of 7 (0.9 %). It comes from 3,000-token prompts occupying
~3 % more of a 175K-token KV pool. It does not come from any notion of pending prefill work, so it would flip on
anything that raises S's KV usage by ~3 points (e.g. longer outputs on S). This is a snapshot at 2 + 3 in-flight
requests. Long-output (where L's KV grows further) was not run.

**Token-load profile (threshold 8192, weight 4) — computed offline, with caveats.** Its input can be rebuilt here
because every request was dispatched by this client. `inflight-load-producer` with the default
`addEstimatedOutputTokens=false` holds a request's estimated prompt tokens from dispatch until its first response chunk
(`framework/plugins/requestcontrol/dataproducer/inflightload/producer.go:420`). With no tokenizer configured the estimate
is `(len(role) + len(content)) / 4` bytes (`…/dataproducer/tokenizer/estimate.go:35, 66, 148-153, 248-258`). The score is
`1 − min(tokens, 8192) / 8192` (`…/scorer/tokenload/token_load.go:115-123`).
- Result: **S on 9 / 10, L on 1 / 10.** On the one L pick, S had two short prompts in flight (154 estimated tokens, 515 real) while L had none.
- Caveat 1: the phase-locked probes always found L's long prompts already streaming, so L's token load was 0 at every
  probe. A random arrival would find L loaded 68 % of the time.
- Caveat 2: the bytes/4 estimate counts a 3,057-token long prompt as **954** tokens (3,810 bytes). This P8 text is
  ~1.25 bytes per real token, so the estimator under-counts it 3.2×.

## Does NOT show

- No EPP and no gateway in the path. Router choices are formulas applied offline to real gauges. EPP behaviour that
  depends on its own scrape timing (50 ms refresh, staleness) is not exercised, and there is no gateway hop in TTFT.
- One box (one Kaggle VM), two replicas, one model (Qwen2.5-3B FP16) on T4 with TRITON_ATTN. Not representative of
  larger GPUs, FlashAttention backends or bigger models.
- GPU state comes from sampled NVML (1 Hz `gpu_sampler`), not DCGM. The two GPUs ran at different SM clocks.
- TTFT under load is phase-locked (above): no valid "random arrival forced to L" TTFT. n = 5 per server in main.
- No long-output (decode-heavy) condition and no size / in-flight sweep.

## Rerun plan and prediction (written before the second push)

Changes for run 2. Same model, revision, vLLM and prompts; one Kaggle session.
- **Probe timing:** `--gate-mode once`. The 5 s hold runs once per condition, then each probe waits a seeded uniform
  0–8 s delay, independent of the background cycle. This fixes the phase-locking of run 1.
- **Conditions, in order:** idle, main, longout (512-token background outputs), and **mns2**. For mns2 both servers are
  restarted with `--max-num-seqs 2`, the simulator's slot count in P8. mns2 is **not vLLM's default**. It is a separate
  question: when slots are limited, does a real engine queue the probe the way the simulator did? It is reported as its
  own row, never mixed with the default-flag rows.
- **Install:** `--installer uv`, falling back to pip, which took ~17 min in run 1.
- **Headline metrics:** TTFT, with e2e secondary. ITL is not an L-vs-S metric, because the two GPUs ran at different
  clocks (idle ITL 32 vs 44 ms in run 1); it is kept only as evidence of prefill stalls.

Prediction. Inputs are from run 1 (20261022-211450): long request TTFT p50 4.22 s; L cycle ~7.7 s; L has a long request
dispatched but not streaming 68 % of the time; short request e2e p50 2.24 s; bytes/4 estimate 954 tokens for a long
prompt and 77 for a short one.
1. **main (default flags, random arrival).** About 2 / 3 of L probes land behind an in-progress 2,048-token-chunk
   prefill. vLLM schedules running requests first, so these wait for it: 0.5–5 s. The rest see ~0.19 s, as in run 1.
   - Median TTFT(L): **1–3 s**, max ~5 s.
   - Median TTFT(S): ~0.14 s, max ≤ 0.4 s.
   - Gap: **~1–3 s**, ratio ~7–20×.
   - Router (offline): stock profile → S (kv scorer only, as in run 1). Token-load → S whenever L has a long prompt in
     prefill.
2. **longout (512 out).** L's cycle is ~4.2 s of prefill plus ~512 × 40 ms of decode, ≈ 25 s, so L is prefilling less
   of the time (~17–34 %).
   - Median TTFT(L): ~0.2–0.5 s.
   - p95 / max TTFT(L): seconds (behind a prefill).
   - Median gap: smaller than main; tail gap: large.
   - KV on L grows above main's 0.035.
3. **mns2 (`--max-num-seqs 2`).** L always runs 2 long requests, so the probe queues until one finishes. That frees a
   slot, and FCFS gives it to the probe ahead of the re-sent long request.
   - Median TTFT(L): **3–5 s**, max ~8 s (one long cycle).
   - S runs 2 shorts with 1 waiting, so its probe waits for ~2 short completions: median TTFT(S) **~1–2.5 s**.
   - Gap: **~1.5–3.5 s**.
   - Router (offline): waiting L 0 vs S 1, so the queue scorer gives L +2 and the stock profile picks **L**: P8's
     mechanism, on a real engine.
   - Token-load: L's long prompt is counted as only ~954 bytes/4 tokens, so its token-score penalty is at most
     ~4 × 954 × 2 / 8192 ≈ 0.93, less than the queue scorer's 2. **So the token-load profile also picks L here**, unlike
     the simulated P8, where it fixed the choice.

### What this says for P8

- **With vLLM defaults, the stock profile does not make the P8 mistake on these gauges.** Nothing queues, and the kv
  scorer alone leans to S (24 / 24, by 0.06 of 7). But a request that *does* land on L pays a median **+2.17 s** to
  first token (16×) and +9.5 s for a 128-token answer. Nothing in the router's inputs measures that cost; the margin
  that avoids it is incidental.
- **With slots limited (`--max-num-seqs 2`, the simulator's setting), the stock profile makes the P8 mistake on real
  engines** (21 / 24 to L). The upstream token-load scorer as configured does not fix it (23 / 24 to L), because the
  bytes/4 estimate undercounts these prompts. The cost on L in this setting is clear in e2e (+6.6 s); in TTFT it is
  +0.94 s at the median and not resolved at n = 12, because S also queues.
