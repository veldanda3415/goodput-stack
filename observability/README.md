# observability/

kube-prometheus-stack, scrape config for the gateway / EPPs / engines, the inference dashboard and the EPP alerts,
on the single-node k3s lab. Everything here was measured on 2026-10-14; sim-pool results are **SIMULATED**.

## What's installed

| Component | Version (pinned in the Makefile) | Source of the version |
|---|---|---|
| kube-prometheus-stack (release `kps`, ns `monitoring`) | chart **92.6.0** (`KPS_VERSION`), Prometheus Operator v0.94.1, Prometheus v3.15.0, Grafana 13.2.4 | `helm search repo prometheus-community/kube-prometheus-stack --versions` on 2026-10-14: latest 92.7.0, so one behind; image tags from the pod events |
| Our objects | `servicemonitors/` (sim, llama.cpp, both EPPs; PodMonitor for agentgateway), `alerts/epp.yaml`, dashboard ConfigMap `inference-dashboard` (ns `monitoring`) | this repo |

Sizing (`values-kps.yaml`): Prometheus retention 2 d / 2 GB, emptyDir (data lost on pod restart), requests+limits on every
component (Prometheus limit 1.5 GiB), 15 s default scrape / 5 s for our targets. k3s-embedded control-plane jobs (etcd,
scheduler, controller-manager, kube-proxy) are disabled: they have no separate endpoints on k3s and would sit DOWN.

## Bring-up

```bash
make obs-up        # helm upgrade --install kps (pinned) + make obs-apply
make obs-apply     # monitors, PrometheusRule, dashboard ConfigMap (rebuilds inference.json from dashboards/dashboard.py)
make obs-down      # remove our objects + the release (CRDs stay)
python3 observability/promq.py targets --wait inference   # every inference target up?
kubectl -n monitoring port-forward svc/kps-grafana 3000:80   # Grafana: admin / lab-only-admin (lab only), dashboard "goodput-stack / inference"
```

The chart's backend NetworkPolicies must allow Prometheus (`networkPolicy.allowFromNamespaces` in
`deploy/charts/inference/values.yaml`); see "Failures" below.

## Alerts (`alerts/epp.yaml`)

| Alert | Expression (short) | for | Why |
|---|---|---|---|
| `EPPUnavailable` | `kube_deployment_status_replicas_available{deployment=~".+-pool-epp"} == 0` | 30 s | FailOpen (GAPS.md P2): the gateway keeps serving 200s, load-blind. Scaling to 0 removes the scrape target, so `up` disappears instead of going to 0, hence kube-state-metrics |
| `EPPFailOpenServing` | the same, joined with gateway request rate > 0 for that pool | 30 s | load-blind routing is happening right now |
| `EPPScrapeDown` | `up{job=~".+-pool-epp"} == 0` | 1 m | pod exists but /metrics doesn't answer |

Proof (`alert_test.py --epp sim-pool-epp`, raw `evidence/alert-test-20261014-221617.jsonl`, SIMULATED backend):
`sim-pool-epp` scaled to 0 at 22:16:47 → both alerts **pending** at 22:16:52 (activeAt), **firing** at 22:17:23
(36.0 s after the scale), EPP restored at 22:17:43 → alerts gone 8.0 s after the EPP was Ready. Client: 176/176 HTTP 200
(55 baseline, 103 while the EPP was down, 18 after).

## Who measures TTFT (#3)

Three components can time a request, and they measure different things. Measured on the k3s lab
2026-10-14 (sim-pool is **SIMULATED**):

| Component | Metric | Starts | Ends | Includes queue wait? | Pools |
|---|---|---|---|---|---|
| Client | `scripts/stream_client.py`, `autoscaling/loadgen.py` (first non-empty `delta.content`) | before the request is sent | first content token | yes, and gateway + EPP + network | both |
| Gateway (agentgateway v1.6.0) | `agentgateway_request_duration_seconds` | request received | **end of the stream** | yes | both |
| Engine (sim) | `vllm:time_to_first_token_seconds` | request scheduled | first token | **no** (`vllm:request_queue_time_seconds` is separate) | sim-pool only |
| Engine (llama.cpp b11146) | none: no histograms, only `timings.prompt_ms` per response | | | | |

Evidence:
- The gateway histogram ends at the end of the stream: one 120-token streaming request grew its `_sum` by 1.9356 s,
  with client total 1.936 s and client TTFB 0.033 s (curl `-w '%{time_starttransfer} %{time_total}'` + two scrapes of
  `:15020/metrics`). agentgateway exports no TTFT/first-byte histogram for these routes; `upstream_call_duration_seconds`
  has no series. So the dashboard puts **engine TTFT next to gateway e2e**, not next to a gateway TTFT.
- The sim's TTFT leaves out queueing: under 6 parallel streams (`stream_client.py -np 6 --runs 12 --max-tokens 96` through
  the gateway) client TTFT p50 was 1,540.2 ms / p95 2,324.3 ms, while engine TTFT p95 peaked at 0.0855 s and engine
  queue time p50 was 1.34–1.75 s (`evidence/task2-load-sim-pool.txt`, `evidence/panels-20261014-222133.json`; queue time:
  `evidence/panels-20261014-222151.json`, `export_panels.py --minutes 6 --panel "queue time"`).
  Client TTFT ≈ queue time + engine TTFT + gateway/EPP/network.
- `agentgateway_request_processing_seconds` (before the upstream call) includes the EPP ext-proc round trip:
  mean 1.354 ms with the EPP up (n=55) vs 0.21 ms with it scaled to 0 (n=103) (`alert_test.py`,
  `evidence/alert-test-20261014-221617.jsonl`). It is the only proxy for EPP decision latency; the EPP exports none.

## Failures diagnosed (runbook)

| Symptom | Evidence | Cause | Fix |
|---|---|---|---|
| node-exporter pod `CreateContainerError` | `kubectl -n monitoring get events`: `failed to generate spec: path "/" is mounted on "/" but it is not a shared or slave mount` | WSL2 root mount is private (`findmnt -o TARGET,PROPAGATION /` → `/ private`); the chart mounts `/` with `mountPropagation: HostToContainer` | `prometheus-node-exporter.hostRootFsMount.enabled: false` (filesystem metrics then show the container's view) |
| inf-llamacpp / inf-vllm-sim targets DOWN | targets API: `Get "http://10.42.0.14:8080/metrics": dial tcp 10.42.0.14:8080: connect: connection refused`; from a curl pod in ns `monitoring`: backends `curl exit 7`, EPP (no netpol) `200`; from the k3s host both answer | backend NetworkPolicies allow only `podSelector`s, i.e. pods in ns `inference`; Prometheus runs in `monitoring` | chart `networkPolicy.allowFromNamespaces: [{namespace: monitoring, podLabels: {app.kubernetes.io/name: prometheus}}]` (L4: it opens the whole API port, not only /metrics) |
| KEDA operator restarted once at install | `lastState.terminated.exitCode 0`, log `Secrets have been updated; exiting so pod can be restarted` | first-start cert rotation, by design | none |

## Known limits

- No GPU metrics: there is no DCGM exporter on the laptop. GPU utilisation / memory panels only make sense with the
  fake-gpu-operator (scheduling/, later) or a real GPU node; none are on the dashboard yet.
- Single Prometheus replica, emptyDir storage, 2 d retention: lab only.
- The sim's TTFT excludes queue time and its KV usage stays at 0; treat sim-pool latency panels as SIMULATED.
- Summed per-pod gauges (queue depth) can over-count at the instant a request moves between pods, because each pod is
  scraped at a different time: 10 seen with 8 clients (sim-pool), 7 with 6 (llamacpp-pool). See autoscaling/README.md.
